## 1. 产品定位

**一句话定位**：一个给"脑洞型玩家"玩的奇术对战平台——异闻师自写奇术（想写什么就写什么，多门奇术尽数登场），随机摇签一位对家，由 LLM 铺陈一段江湖故事；对决期间奇术保密，败方凭行迹线索猜对家奇术，猜中则逆转胜负。纯机制对抗、无数值强度，靠脑洞与心理博弈驱动。

- **目标用户**：脑洞/脑力型玩家，小圈子（给朋友玩）。
- **核心爽点**（按优先级）：
  1. **奇术保密 + 猜奇术**：行迹叙述既不能明说对家奇术、又要给出可辨识的线索——读行迹、猜奇术本身就是博弈。
  2. **自由创作奇术**：零门槛输入、无限脑洞，机制完全由玩家自己设计。
  3. LLM 铺陈的江湖故事。
- **明确不做**：不逼氪（无充值）、不做实时联机（无 WebSocket）、不做抽卡收集、不做奇术融合、不做数值/强化系统（对决纯机制对抗）。

## 2. 核心循环

```
异闻师写下自己的奇术（名称 + 效果，自由文本，存入奇术篇）
        ↓
装入奇人并解封（初始 3 槽，每 50 见闻 +1，上限 8；同一奇术可入多位奇人）
        ↓
启程（后台摇签对家）→ LLM 铺陈战局（约 10-30s）
        ↓
阅读行迹（对家奇术保密 🔒，仅凭行迹中的线索）
        ↓
败方获窥秘机会，逐次猜对家实际使用的奇术 → LLM 语义匹配上卡
        ↓
全破 → 胜负逆转 + 重算名望（Elo）+ 双方奇术被看破
未全破 → 按被猜方设置决定是否被看破
        ↓
名望（Elo）结算 + 见闻积累（每场 +5、首场额外 +5，满 50 解锁新奇人槽）→ 再战
```

## 3. 功能设计

### 3.1 用户系统
- 注册 / 登录（JWT + bcrypt）。
- **每日登录开张**：当日首次登录/访问自动 +10 见闻。
- 数据隔离：仅本人可操作自己的奇术、发起自己的对战、提交自己的猜测。

### 3.2 奇术系统（用户自定义）
- **奇术形态**：`名称`（≤50 字）+ `效果`（≤500 字），纯自由文本，想写什么就写什么。
- **奇术篇**：一个用户可持有多个奇术，全部存入奇术篇。
- **奇人（角色）**：注册即得 3 个奇人槽位，可新增（每 50 见闻 +1 槽、上限 8，见 §3.6）；奇术可自由装入任意一位（同一奇术可入多位）。每位奇人一个 `enabled`（已解封）开关——**已解封 = 可主动启程，且进入台下听客（匹配池）**；全部未解封则既不能发起对决、也不会被摇签。对战时从「已解封且非空」的奇人中随机抽一位登场（发起方与对家共用同一逻辑）。奇人另有「姓名 / 战斗风格」字段（v3.2 已实现），未命名时前端显示占位名「奇人·壹/贰/叁」。
- **内容去重**：奇术 id = `sha256(user_id:name:effect)[:16]`——同用户同内容幂等共享一条 `abilities` 记录；不同用户可各自拥有相同内容的奇术。
- **接口**：
  - `POST /api/abilities` 新增（幂等，重复提交返回已有记录）
  - `GET /api/abilities/mine` 我的奇术集
  - `PUT /api/abilities/{id}` 修订（id 保持稳定，不影响历史行迹记录）
  - `DELETE /api/abilities/{id}` 删除；不再被任何用户/奇人持有时清理 `abilities` 本体
  - `GET /api/loadouts` 我的奇人列表（含已解封开关与奇术）
  - `PUT /api/loadouts/{id}` 切换已解封 `enabled`（兼存 `tactic` 战术）
  - `POST /api/loadouts` 新增奇人（超过槽位上限则 400「见闻不足，未能解锁更多奇人槽位」）
  - `POST /api/loadouts/{id}/abilities/{ability_id}` 装入奇人 / `DELETE` 卸下
- 遗留字段 `seed/description/activation/hand_motion/target_attribute/target_relation` 已随 v3 清理；奇术仅含 `name/effect`。

### 3.3 启程（对战）系统
- **启程**：`POST /api/battles`（后台自动摇签对家）或 `POST /api/battles/challenge/{user_id}`（切磋故人，**不计名望**）。
- **无需在线**：对家是听客池中的"数据快照"，任何一方都不需要实时在线。
- **登场抽取**：双方都从各自「已解封且非空」的奇人中随机抽一位登场（v3 已合并旧的「参与匹配 / 使用位」双开关为一个 `enabled`）。
- **铺陈**：创建 `pending` 记录 → 后台异步任务调用 LLM 铺陈战斗叙述（战场场景服务端随机，第三人称、以发起方 A 为观察视角）→ 结算落库 `done`（失败标记 `failed`）。推演中前端经 SSE 逐段接收自己视角的叙述。
- **胜负**：一方被击杀或彻底失去战斗能力；僵持不下可**和局**（和局无败方、**不可猜奇术**）。
- **切磋**：`friendly=true`，不计名望，其余流程一致（含猜奇术翻转）。

### 3.4 猜奇术系统（核心 · 窥秘）
- **触发**：战败方（非和局）在行迹页获得「窥秘一刻」机会，逐次道出猜测（提交对家**实际使用过**的奇术线索）。猜测次数为后端硬上限（不向前端展示）。
- **点评**：每次道出猜测，LLM 依据「猜测全文 + 实际使用的能力」输出一段点评——说对了哪些 / 说错了哪些 / 哪些是包含（过宽）/ 哪些是小于（过窄）/ 哪些是偏移。**点评只围绕用户说过的话展开，绝不透露新信息**（不泄露能力真名/效果原文）。
- **点评判定值**：原子点评只使用「是 / 否 / 部分是 / 不能确定」；“部分是”表示方向相关但表述不精确或不完整。
- **检定**：独立动作，由玩家**主动发起**。依据「全部猜测+点评」聊天记录，对每门未看破奇术判定——已看破（揭示该门真实奇术）或指出还缺什么。发起检定后需再道出新猜测并得到点评，才能再次检定。
- **猜中（全破）**：检定使全部奇术看破 → 胜负直接逆转（输家变胜者、原胜者落败）＋ **按新结果重算 Elo 名望**（随机对局；切磋不结算）＋ 双方奇术**必看破**（作为确认）。
- **未全破**：次数耗尽仍未全破 → 双方奇术是否揭示由**被猜方（当前胜者）的设置** `reveal_on_miss` 决定（默认展示）。
- **状态机**：`guess_state` 为 `none` → `guessing`（至少猜一次）→ `done`；次数用尽即结束。

### 3.5 奇术保密与看破
- 对决结束（且判定完成）前，**任何一方都看不到对方的奇术表**。
- 行迹 API 按查看者身份过滤（`_filter_story`）：自己一侧奇术始终可见，对家一侧仅在看破后可见；**公开传阅页**在看破前双方奇术表全部隐藏。
- 行迹落盘 md 在看破前写「未看破——等待输家猜奇术，猜中可逆转胜负」，不含对家奇术。
- **看破时机** = 败方发起检定且判定完成（检定看破必看破；收手未全破按被猜方设置）。

### 3.6 数值系统（名望 / 见闻）
- **名望**（天梯 Elo，K=32，起始 1000）：仅用于排名；**随机对局结算、切磋不结算**；猜奇术翻转时按新结果重算。
- **见闻**（唯一养成属性）：每日登录开张 +10、每场对战 +5、当日首场额外 +5；**满 50 见闻解锁 1 个新奇人槽**（初始 3 槽、上限 8）。
- 赏钱/积分、段位/等级已随 v3.4 移除；对决纯机制对抗，**没有任何提升战斗力的数值消耗**。

### 3.7 故人系统
- 故人拜帖（申请）/ 接受 / 列表 / 待收；向故人切磋（友谊局）。

### 3.8 LLM 集成
- OpenAI 兼容协议（默认 DeepSeek），平台统一 Key 由 `.env` 配置（`LLM_API_KEY` / `LLM_BASE_URL` / `LLM_MODEL`）。
- JSON 输出（`response_format=json_object`）+ 空内容/解析失败自动重试 + 限流/超时指数退避 + 降级非 JSON 模式兜底。
- 战斗推演与猜奇术判定用**思考关禁用**（`thinking=False`，提速降本，质量由 prompt 补偿）。
- BYOK（用户自带 Key 覆盖）为设计项，尚未接入。

## 4. 技术架构

### 4.1 技术栈
- 后端：FastAPI（Python 3.12，uv 管理）+ SQLAlchemy 2.0 async + aiosqlite + Alembic 迁移 + Pydantic v2。
- 前端：Vite + React + TypeScript，移动端响应式。
- LLM：统一适配层（`app/services/llm/client.py`），DeepSeek 默认。

### 4.2 后端模块划分（app/）
```
app/
├── api/            # 路由：health, auth, abilities, loadouts, battles, friends
├── core/           # 配置（.env）、安全（JWT/bcrypt）
├── db/             # 引擎、会话（Base / async_session_factory / get_db）
├── models/         # ORM：user, ability, user_ability, loadout, loadout_ability, battle, friendship
├── schemas/        # Pydantic 校验
└── services/
    ├── ability/        # 奇术三相解析
    ├── loadouts/       # 奇人装配与风格/战术清洗
    ├── battle/         # 对局生命周期、推演编排、SSE、Elo、摇签
    ├── guess/          # 猜词编排
    ├── llm/            # 模型客户端、可靠性与密钥加密
    ├── admin/          # 测试战场与提示词调试
    ├── support/        # 通知
    └── nodes/          # 按奇术、推演、猜词分组的 LLM 节点
```

### 4.3 核心数据模型
- **users**：id, username, password_hash, exp（见闻）, rank_points（名望）, last_login_date, last_battle_date, **reveal_on_miss**, created_at（`level`/`score` 已随 v3.4 删列；奇人槽位上限由属性 `max_loadouts = 3 + exp//50`（封顶 8）推导）
- **abilities**：id（内容哈希）, name, effect, detail, tactic, understanding, created_at
- **user_abilities**：（user_id, ability_id）复合主键, obtained_at
- **loadouts**：id, user_id, **name**（奇人姓名，默认 ''）, **style**（战斗风格，默认 ''）, **enabled**（已解封，默认 1）, **tactic**, created_at —— 注册时补 3 位，可新增（上限 8，见闻解锁，见 §3.6）
- **loadout_abilities**：（loadout_id, ability_id）复合主键, added_at —— 奇术 ↔ 奇人 多对多
- **battles**：id, user_a_id, user_b_id, winner_id, status（pending/done/failed）, story（JSON：narration_a/b/winner/abilities_a/b/insight_a/b）, rank_delta_a/b（名望 Elo 变化）, **loadout_a_id / loadout_b_id**（本场奇人快照）, **friendly**, **guess_by**, **guess_text**, **guess_state**, **guess_hit**, **guess_score**, **revealed**, share_token, share_token_b, created_at
- **battle_guesses**（battle_id 主键，结算时与 done 同事务预建）：used_abilities（赢家实际使用的奇术子集，服务端保密）, cards（逐卡进度 `{matched, progress, cracked}`）, attempts_used / attempts_max（默认 5）, flipped（全破逆转）
- **friendships**：（user_id, friend_id）复合主键, status（pending/accepted）, created_at

### 4.4 关键实现要点
- **后台异步推演**：`start_battle` 创建 pending 记录后 `asyncio.create_task` 推演，任务引用存入模块级集合防止被 GC 取消；推演失败静默标记 `failed`，不抛给用户。
- **奇术保密**：`story` 全量落库，API 层按查看者身份过滤后再返回（`_filter_story(story, viewer_id, revealed, a_id, b_id)`）。
- **猜奇术原子性**：`submit_guess` 在同一会话内完成「道出猜测 → LLM 匹配上卡 → 进度达门槛看破 → 全破则翻转胜负 + 重算名望 → 更新 revealed → 重写行迹 md」。
- **迁移**：新增/修改列一律走 Alembic 迁移；`Base.metadata.create_all` 不会给已存在的表加列。
