# 清理记录 · 第二站：migrations/

> 2026-09-18 清理。这一站和别站性质不同：迁移文件是数据库的**历史档案**，删改历史本身就是事故，
> 所以本站几乎没有"删"，重心是**链路健康审计**和**留下一份能看懂的全链说明书**。
> 验证方式：`alembic heads`（单一 head）+ `alembic current`（库在最新）+ `alembic check`（模型与库零漂移）。

## 一、先说清楚：迁移是什么

`app/models/` 里的 Python 类只是数据库结构的"图纸"。真实数据库不会自己跟着图纸变——每次改结构（建表、加列、删表）都要写一份**带编号的变更记录**（迁移文件），按顺序执行。`migrations/versions/` 里的 35 个文件就是这样一串记录，用 `down_revision` 一个指向一个，串成一条单向时间线。

规矩（已写进本目录 README）：
1. 已应用的迁移**永不修改、永不删除**——老库靠它一步步走过来，改了历史，老库就断了路。
2. 改完模型先跑 `alembic check` 看漂移，再自动生成迁移并**人工复核**（自动生成的回滚常有坑）。
3. 新迁移必须接到当前唯一 head 上，保持单链。

## 四、给后来者的话

- 想知道库现在在哪：`uv run alembic current`；想看这条时间线：`uv run alembic history`。
- 全库推倒重建也不用怕：`alembic downgrade base` 再 `upgrade head` 能走完全程（个别老迁移的 downgrade 是"结构复原、数据不还"的尽力而为实现）。
